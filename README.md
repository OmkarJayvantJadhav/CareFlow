# CareFlow

> **Demo with a fictional hospital. Not for medical use.** All patients, doctors and schedules are synthetic.

CareFlow is a hospital assistant for OPD (outpatient) visits at the fictional
**Indravani General Hospital**: patients book, reschedule and cancel appointments
through conversation in English, Hindi or Marathi, get cited answers from hospital
documents, and see a live queue with predicted waiting times. Every behaviour is meant
to be proven by an automated evaluation suite.

The full specification is in [`docs/CareFlow-Project-Documentation.md`](docs/CareFlow-Project-Documentation.md).
Decisions taken where the spec is silent are in [`docs/DECISIONS.md`](docs/DECISIONS.md).

### What works

- **Web app (`ui/`)** — the nine screens of docs §8 in English, हिन्दी and मराठी, phone-first for
  patients and desktop-first for staff, served by the API on the same port:
  - *Patient / caregiver:* language and role picker, chat with confirmation cards (Confirm / Change, with a
    countdown), citation chips that open the source, progress steps, "Talk to a person", an emergency panel
    that takes over the chat, My appointments (changes go through the chat so they get a card), and a live
    queue page (token, people ahead, "about 35 min (25–50)", doctor status) over a WebSocket with polling fallback.
  - *Front desk:* today's doctors and bookings, check-in, walk-in registration, call next / start / end /
    missed / returned, priority; doctor break, delay, resume and "unavailable today".
  - *Admin:* live queues, delays and no-shows per department, the latest evaluation results, recent latency
    and cost, demo reset, and analytics questions answered with the generated SQL shown and CSV export.
  - Large-text mode (double size), 44 px tap targets, works at 360 px wide, screen-reader labels, a demo
    banner on every page; checked automatically with axe-core (no serious or critical WCAG A/AA issues).
- **Chat (`POST /api/v1/chat`)** — a hand-written tool-calling agent (`app/agent/`) with argument
  validation, a step limit, a token budget and a JSON trace of every LLM and tool call.
  - **Confirmation is enforced in code:** the model can only *propose* a booking, change, cancellation or
    waiting-list entry. CareFlow checks it for real (in a rolled-back preview), shows a confirmation card,
    and executes only after the user's explicit "yes" or a tap on Confirm. Cards expire after 5 minutes.
  - **Safety gate before planning:** every message is checked for emergencies (English, Hindi, Marathi,
    romanised) by symptom patterns checked clause by clause and a classifier trained on separately written
    examples. An emergency gets fixed guidance (112 / 108) with no LLM call and no writes. Medicine names
    and doses never reach the user. "Talk to a person", and three failed turns in a row, create a handoff ticket.
  - **Cited answers:** policy, insurance, preparation and facility questions are answered from the knowledge
    base with citations. A reply that cites none of the retrieved sources is replaced, in code, by "I couldn't
    find that in the hospital's documents" and an offer of a person. Instructions hidden in documents are removed
    before the model sees them.
  - Replies come in the user's language; roles and ownership are enforced inside every tool.
- **Knowledge base** — 357 documents (119 topics in three languages, six collections) generated by
  `simulator/kb/`. Policy numbers and doctor timetables come from the same code the booking rules use.
- **Hybrid retrieval** (`app/rag/`) — pgvector dense search + BM25, rank fusion, a multilingual
  cross-encoder re-ranker, the user's-language version of each cited section, and a relevance threshold.
  When the neural models cannot be downloaded it falls back to local models automatically.
- **LLM providers** — Groq (primary), Gemini (fallback) and Ollama (local) behind one interface. A 429 or
  503 is retried once, then served by the fallback; if every provider fails, `/chat` returns 503.
  Free-tier quotas are small (on 19 Oct 2026 the Gemini free tier allowed 20 requests per day for
  `gemini-3.5-flash`), so a Groq key is recommended for the primary.
- **REST API** — demo login, doctor search, slots, book / reschedule / cancel, history, waiting list,
  health. These endpoints share the agent's service functions, so the rules are identical.
- **Live queue** — staff endpoints for walk-ins, check-in, calling, consultations, missed turns, priority
  and doctor events. Every change is pushed over a WebSocket (`/ws/queue/{session}`) as queue, prediction and
  doctor-status updates, with a polling fallback. A doctor's break never reorders the queue.
- **Wait-time prediction** — after every queue event each waiting patient gets an estimate with a
  range ("about 35 min (25–50)") from a LightGBM model trained on 90 simulated days. When three people
  are ahead, a (mocked) "your turn is near" message is sent. The agent can answer "how long is my
  wait?" and offers rebooking when a doctor becomes unavailable.
- **Admin analytics (`POST /api/v1/admin/analytics`)** — questions answered with one validated, read-only
  SELECT over reporting views without patient names or phone numbers, run as a SELECT-only database role in a
  read-only transaction with a timeout and row limit. Requests to change data are refused before any LLM call.
- **Evaluation suite (`eval/`)** — 120 agent scenarios with a simulated patient and code-checked outcomes,
  150 RAG questions, 280 safety cases (including two held-out emergency sets), a baseline mode without the
  code-level safeguards, and a resumable runner that works within free LLM quotas (see `eval/README.md`).
- From Phase 1: the database, booking rules, queue engine, audit log, masking and simulator.

cross-validated). Agent scenarios and graded RAG answers are still running: free quotas allow about
25–30 agent conversations a day, so those numbers grow daily and always state how many runs they rest on.

### What has and has not been verified

- **Verified here:** 316 automated tests on Python 3.11 and 3.13, including 33 agent scenarios with a
  scripted LLM (booking end to end, cards, expiry, slot taken, duplicates, reschedule and cancel windows,
  waiting list, caregivers, injection attempts, citations, unanswerable questions, emergencies, handoff,
  step limits, token budget, queue status), the queue API with live WebSocket updates, and a full simulated
  day with live predictions. The Docker image is built and smoke-tested (LightGBM and the trained model
  load) in CI; the development sandbox cannot reach Debian's package mirrors to build it locally.
- **Real LLM:** the evaluations run real conversations against Groq (`openai/gpt-oss-120b`), with a second
  model playing the patient.
- **Not verified here:** the development environment cannot reach Hugging Face, so the neural embedding and
  re-ranking models have not been loaded; every retrieval number is for the local fallback models.

## Quick start (Docker)

Requirements: Docker with Compose, and an LLM key for chat (a free Groq or Gemini key).

```bash
cp .env.example .env        # put GROQ_API_KEY and/or GEMINI_API_KEY in .env
docker compose up --build
```

On start the container migrates the database, seeds the fictional hospital, loads the knowledge base
(re-embedding only if documents or the embedding model changed) and serves on <http://localhost:8000>:

- **The app:** <http://localhost:8000> — pick a language and a demo role
- Health: <http://localhost:8000/api/v1/health> (`"degraded"` means no LLM key is configured)
- OpenAPI docs: <http://localhost:8000/docs>

Try the chat:

```bash
TOKEN=$(curl -s -X POST localhost:8000/api/v1/auth/demo-login -H 'content-type: application/json' \
  -d '{"role":"patient"}' | python -c "import sys, json; print(json.load(sys.stdin)['token'])")
curl -s -X POST localhost:8000/api/v1/chat -H "Authorization: Bearer $TOKEN" -H 'content-type: application/json' \
  -d '{"message": "Book a Marathi-speaking cardiologist on Saturday"}'
# Reply "yes" (with the same conversation_id), or send {"conversation_id": ..., "confirm_action_id": ...}
```

Demo accounts: `asha` (patient), `rajan` (caregiver, verified for his father Vinayak), `sunil`
(caregiver whose link is unverified, so he is refused), `priya` (staff), `mehta` (admin). Log in with
`{"role": ...}` or `{"username": ...}`.

## Local development

Requirements: Python 3.11+, and PostgreSQL 16 with pgvector (the Compose `db` service is easiest).

```bash
python -m venv .venv && source .venv/bin/activate
pip install -r requirements-dev.txt
cp .env.example .env                       # adjust DATABASE_URL; add an LLM key for chat

docker compose up -d db
alembic upgrade head
python -m simulator seed                   # the fictional hospital
python -m app.rag.ingest                   # the knowledge base
uvicorn app.api.main:app --reload
```

Without internet access to Hugging Face, set `EMBEDDING_BACKEND=local` and `RERANKER_BACKEND=local`
to skip the download attempt (about 40 s) and use the local retrieval models directly.

The UI (Node 22):

```bash
cd ui && npm ci
npm run dev        # http://localhost:5173, proxies /api and /ws to the API on :8000
npm run build      # ui/dist, which the API then serves at http://localhost:8000
```

### Commands

| Command | What it does |
| --- | --- |
| `python -m simulator seed [--if-empty]` | Departments, doctors, demo accounts, 400 synthetic patients, 21 days of slots and bookings |
| `python -m simulator reset` | Demo reset: wipe operational data and reload exactly the same seed |
| `python -m simulator replay-day --date YYYY-MM-DD` | Simulate a full OPD day and check its invariants |
| `python -m simulator history --days 90` | Replay past days without live predictions (training data) |
| `python -m app.ml.train --end YYYY-MM-DD` | Train and evaluate the wait-time model on those days; writes `app/ml/artifacts/` and `eval/results/ml_wait_time.json` |
| `python -m simulator.kb.build` | Regenerate the Markdown knowledge base from `simulator/kb/` |
| `python -m app.rag.ingest [--if-needed] [--chunker structure\|fixed]` | Chunk, embed and load the knowledge base |
| `python -m app.rag.preload` | Download the neural retrieval models (the Docker build does it with `--build-arg PRELOAD_MODELS=true`) |

### Tests

The tests use a real PostgreSQL + pgvector database (they drop and recreate its schema), always use the
local retrieval models, and never call a real LLM:

```bash
docker compose exec db createdb -U careflow careflow_test     # once
export TEST_DATABASE_URL=postgresql+psycopg://careflow:careflow@localhost:5432/careflow_test
pytest
ruff check . && ruff format --check .
```

UI unit tests and browser tests (the browser tests start the app with their own database, a fixed clock
and a stand-in LLM, so they need no API key):

```bash
cd ui && npm run lint && npm test && npm run build && cd ..
pytest -m e2e tests/e2e          # 15 tests: all nine screens, live queue under 2 s, accessibility, 360 px
```

GitHub Actions runs lint, the Python tests, the UI tests, the browser tests and a Docker build on every
push; Render redeploys the demo from `develop` after each push (`docs/DEPLOY.md`).

## Business rules (enforced in code)

| Rule | Value |
| --- | --- |
| Rescheduling | Until 12 hours before the appointment (any time if the doctor became unavailable) |
| Cancellation | Until 4 hours before the appointment |
| Booking window | From 15 minutes to 30 days ahead |
| Duplicate booking | One active appointment per patient, doctor and day |
| Waiting list | A freed slot is held for the earliest matching waiting patient for up to 2 hours |
| Late arrival | More than 15 minutes after the slot start → queued by arrival time |
| Confirmation | Every change needs an explicit yes to a card that expires after 5 minutes |
| Emergencies | Guidance (112 / 108) before anything else; no writes in that turn |

## Limitations

- Synthetic data only; the simulator's parameters are assumptions (`docs/DECISIONS.md`, D-21).
- No neural-model retrieval has been run in the development environment (Hugging Face is unreachable
  there); every retrieval number is for the local fallback models.
- The agent evaluation runs within free LLM quotas, so its numbers grow over several weeks; each states
  how many runs it rests on.
- The local fallback retrieval models handle Marathi inflections less well than the neural models.
- The wait-time model is trained on synthetic days whose queues are short; real OPDs may differ.
- The live WebSocket broadcaster runs in one process (the demo deployment); several API processes
  would need a shared message bus.
- Notifications are mocked (stored in the `notification` table, never sent).
