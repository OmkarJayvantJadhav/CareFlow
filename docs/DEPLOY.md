# Deploying CareFlow on free tiers (docs §12)

There are two ways to run it: the **demo** (`DEMO_MODE=true`, the default: the fictional hospital, demo roles
and a reset button) and **a hospital's own deployment** (`DEMO_MODE=false`, section 3). The steps are the same
apart from a few settings.

The whole app — API, chat, live queue and the React UI — is one Docker image listening on port 7860.
The database is a free Neon Postgres with pgvector. Nothing here costs money; free tiers change, so
check the limits when you deploy.

## 1. Database: Neon (free plan)

1. Sign up at <https://neon.tech> and create a project (region: Singapore, closest to Pune), Postgres only.
2. Copy the connection string from **Connect**. It can be pasted as it is
   (`postgresql://USER:PASSWORD@HOST/neondb?sslmode=require…`); the app switches it to the psycopg driver.
   This is your `DATABASE_URL`. Keep it secret. The pooled string (host with `-pooler`) and the direct one
   both work: CareFlow does not use server-side prepared statements, which a pooler in transaction mode
   cannot carry (D-128), and never keeps a transaction open during slow work, which the database would end
   (D-130).

The first start enables pgvector, migrates the database, seeds the fictional hospital (~20 s; demo mode only)
and loads the knowledge base. Neon's free plan suspends compute when idle; the first request after a pause takes a few
seconds.

## 2. App: Render (free web service)

Hugging Face Spaces now needs a paid plan for Docker apps (D-66), so the demo runs on Render.

1. Sign up at <https://render.com> with GitHub and allow Render to read this repository.
2. **New → Blueprint**, pick the repository. Render reads `render.yaml` (free plan, Singapore, branch
   `develop`) and asks for three values:

   | Name | Value |
   | --- | --- |
   | `DATABASE_URL` | the Neon string from step 1 |
   | `GROQ_API_KEY` | from <https://console.groq.com/keys> |
   | `GEMINI_API_KEY` | from <https://aistudio.google.com/apikey> (fallback provider) |

   `AUTH_SECRET` is generated by Render; `DEMO_MODE` and the retriever settings come from the blueprint.
3. **Apply.** The first build takes about 5–10 minutes. The demo is then at
   `https://careflow-XXXX.onrender.com` (the name is shown on the service page).

Every push to `develop` redeploys. The free instance has 512 MB of memory; the app is configured to use
the local retriever, which the evaluation was measured with, and peaks at about 370 MB (D-67). It sleeps
after 15 minutes without visitors; the first request then takes about a minute.

**Check from a fresh browser (the Phase 5 gate):** open the link in a private window → pick a language and
"Patient" → ask "Book a Marathi-speaking cardiologist on Saturday" → confirm the card → see it under
My appointments. `/api/v1/health` should say `"status": "ok"`.

## 3. A hospital's own deployment

Use a separate Neon project (never the demo's database) and a separate Render service. In the service's
**Environment**, set:

| Name | Value |
| --- | --- |
| `DEMO_MODE` | `false` |
| `AUTH_SECRET` | a long random value (Render can generate one) |
| `DATA_KEY` | another long random value (`python -m app.manage new-data-key`); it encrypts patients' phone numbers. Keep it safe and do not change it: numbers stored with an old key can no longer be read |
| `INITIAL_ADMIN_USERNAME` | the first administrator's username, e.g. `admin.sharma` |
| `INITIAL_ADMIN_PASSWORD` | a temporary password of at least 8 characters |
| `INITIAL_ADMIN_NAME` | their name as shown in the app |
| `ALLOW_REGISTRATION` | `true` to let patients and caregivers sign up themselves, `false` for desk registration only |

At every start the app checks whether an admin can sign in. Only if none can does it create this admin, who
must choose a new password at the first sign-in. The variables can stay set afterwards; they change nothing
once an admin exists. Render's free plan has no shell, which is why the first admin comes from the
environment. With a shell, `python -m app.manage create-admin --username U --name "…"` does the same and
prints a temporary password once.

The admin first opens **Hospital setup**: the hospital's name (in English, and in Hindi and Marathi if you
like), address, reception phone and hours, and one sentence per language on where the emergency department
is; then each department with its OPD hours, and each doctor with their languages, OPD days and appointment
length. Slots open from the next day. Then **Accounts**: the front-desk, doctor and other admin accounts. Each gets a
temporary password, shown once, to hand over in person or by phone; it must be replaced at the first sign-in.
A forgotten password is reset there in the same way. Switching an account off ends its sessions immediately.

**Patient data and the assistant.** In chat, messages (with phone numbers masked), the names of the patients
being helped and their appointment details are sent to the LLM provider you configure (Groq and Gemini on the
free plans). Decide whether that is acceptable for your patients. If not, use a provider you have a
data-processing agreement with, or a local model (`LLM_PRIMARY=ollama:<model>`, `OLLAMA_BASE_URL`). Booking,
queues and every other screen work without it.

Then **Hospital setup → Booking and queue rules** for your cut-offs and windows, and **Documents**: the
information documents start as the demo hospital's. Edit the ones that apply (policy numbers follow your
rules automatically), hide the ones that do not (the demo's departments, doctors, facilities and insurers),
and add your own. Changes are live at once. The demo reset and the demo roles are switched off in this mode.

### Messages by SMS and e-mail

Every message is shown in the app. To also send them, set a provider in the environment, then turn sending on
under **SMS and e-mail** and choose the kinds (reminders, changes to a visit, queue updates, waiting-list
offers). Nothing is sent until both are done, and the real providers never send in demo mode.

| Name | Value |
| --- | --- |
| `SMS_PROVIDER` | `none` (default), `log` (written to the server log, to try it out), `twilio` or `webhook` |
| `TWILIO_ACCOUNT_SID`, `TWILIO_AUTH_TOKEN`, `TWILIO_FROM` | for `twilio`: the account, its auth token and the sending number |
| `SMS_WEBHOOK_URL`, `SMS_WEBHOOK_SECRET` | for `webhook`: your SMS gateway's address and a shared secret |
| `EMAIL_PROVIDER` | `none` (default), `log` or `smtp` |
| `SMTP_HOST`, `SMTP_PORT`, `SMTP_SECURITY` | the mail server, port (587) and `starttls` (default), `ssl` (port 465) or `none` |
| `SMTP_USERNAME`, `SMTP_PASSWORD`, `SMTP_FROM` | the sign-in (if the server needs one) and the sender address |

* **E-mail** is the free option: any SMTP service works, e.g. a mailbox with an app password, or a
  transactional mail service's free plan. Patients add an address and choose e-mail under **My profile**.
* **SMS** costs money. Twilio's trial sends only to numbers verified in its console. For Indian providers, use
  `webhook`: CareFlow sends `POST {"channel": "sms", "to": "+91…", "text": "…", "reference": "n123"}` with the
  headers `X-CareFlow-Timestamp` and `X-CareFlow-Signature: sha256=<HMAC-SHA-256 of "<timestamp>.<body>" with
  the secret>`; your gateway checks the signature and answers 2xx (optionally `{"id": "…"}`). Commercial SMS to
  Indian numbers need a DLT-registered sender ID and templates, which you and your provider arrange.
* Send a test from the page first. Failures, and messages not sent (too late to be useful, a patient who chose
  "only in the app", no address), are listed there with the reason; failed ones can be sent again.
* Messages are sent by a background task every 20 seconds while the server is awake. Render's free instance
  sleeps after 15 idle minutes, and reminders and queued messages then wait until it wakes. To keep it awake
  during OPD hours, point a free uptime monitor at `/api/v1/health` every 10 minutes (one service running all
  month stays within the free plan's hours).

## 4. Monitoring

* Add a free uptime monitor (e.g. UptimeRobot) on `/api/v1/health` every 30 minutes; alert after two failures.
* The admin dashboard shows median latency, LLM errors and cost for recent chat turns on the server, and the
  latest evaluation results shipped with the build.
* Provider dashboards (Groq console, Google AI Studio) show quota use.

## Runbook

| Situation | Action |
| --- | --- |
| The page says it is waking up / first request is slow | Expected after idle (Render or Neon); wait a minute |
| Chat answers "The assistant is busy right now" | Free LLM quota reached; it recovers within minutes to a day. Check the Groq console |
| Visitors left messy data (demo only) | Admin → Dashboard → **Reset demo data** |
| An admin forgot their password (hospital deployment) | Another admin resets it under **Accounts**. If no admin can sign in, run `DATABASE_URL='<the Neon string>' python -m app.manage reset-password --username U` from a checkout of this repository on any computer; it prints a temporary password once |
| Someone left or a device was lost | Admin → **Accounts** → switch the account off (its sessions end at once) or reset its password |
| A patient asks for their data to be deleted | Admin → **Patients** → find them → **Erase this patient's details**, with the reason. Patients with an account can also do it themselves from their profile |
| A patient asks what you hold about them | They download it from their profile (**Download my data**); otherwise staff read it out from **Patients** |
| A doctor leaves the hospital | Admin → **Hospital setup** → the doctor's **Last day**; later patients are told and rebook free with a colleague. Switch off their account under **Accounts** |
| A policy or opening hour changes | Admin → **Documents**: edit the document and save; for a rule number, change it under **Hospital setup → Booking and queue rules** and every document that states it follows |
| A timetable changes | Admin → **Hospital setup** → edit the department's OPD hours or the doctor's days or appointment length; it applies from tomorrow and lists bookings that no longer fit, which are kept |
| Database suspended (free limit hit) | Wait for the monthly reset, or create a new Neon project and update `DATABASE_URL` |
| A deploy broke the demo | Render → the service → **Events** → roll back to the previous deploy |
| Slots run out on a long-running demo | They should not: the next 21 days are topped up at every start and every 6 hours |
