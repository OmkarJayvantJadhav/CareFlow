# Design decisions

Where the specification (`docs/CareFlow-Project-Documentation.md`) is silent, ambiguous
or contradictory, the simplest option consistent with it is chosen and recorded here.
Each entry names the phase that introduced it.

## Decided before development (PRD open questions)

| ID | Decision |
| --- | --- |
| D-00a | **Queue merge rule:** booked patients keep slot order; walk-ins fill gaps. The rule is configurable (FR-22): `QUEUE_MERGE_RULE=slot_order` (default) or `alternate` (1:1), stored per queue session. |
| D-00b | **LLM provider:** Groq is the default primary; revisit after the first evaluation run. |

## Phase 1 — Foundation

| ID | Topic | Decision | Why |
| --- | --- | --- | --- |
| D-01 | Repository layout | The repository root is the `careflow/` folder of the suggested layout. Added `docker/` (container entrypoint), `alembic/` (migrations), `app/config.py` and `app/timeutil.py`. | Keeps the suggested layout; migrations and container scripts need a home. |
| D-02 | Merge rule, precisely | Three lanes: *priority* (staff-raised, highest first), *booked* (on-time booked patients, by slot time) and *walk-in* (walk-ins plus late or returning booked patients, by arrival time). `slot_order` projects the doctor's day forward one average consultation (the doctor's slot length) at a time, starting no earlier than OPD opening or the end of a break; a booked patient is taken once their slot time has arrived, otherwise the earliest walk-in fills the gap. `alternate` takes one booked, then one walk-in. | Makes "walk-ins fill gaps" deterministic and testable (TC-09). |
| D-03 | Late arrivals and missed turns | A booked patient arriving more than **15 minutes** after the slot start loses slot order and queues by arrival time. A patient who missed their turn and returns queues by return time. | The spec lists these events (FR-23) without rules. |
| D-04 | Policy windows | Reschedule allowed until **12 hours** before the appointment; cancel until **4 hours** before; booking up to **30 days** ahead and at least **15 minutes** before the slot. Values live in `app/tools/policy.py`; the knowledge-base policy documents (Phase 2) must state the same numbers. | The spec requires windows but gives no numbers. |
| D-05 | Reschedule semantics | Rescheduling moves the **same appointment row** to the new slot and sets its status to `rescheduled` (still active). The old slot is freed and offered to the waiting list first. The new slot must be in the **same department**. | Keeps the appointment id stable for `PATCH /appointments/{id}`; matches the `rescheduled` status the schema lists among active statuses. |
| D-06 | Doctor unavailable | Added appointment status **`displaced`**: today's not-yet-seen appointments of that doctor become `displaced`, their queue entries close, the doctor's remaining slots that day become `blocked`, and every affected patient gets a mocked notification. A displaced appointment can be rescheduled (same department) or cancelled **regardless of the policy window**. A patient already in consultation finishes. | FR-27 asks to offer rescheduling; it would be unfair to apply the 12-hour window to the hospital's own cancellation. |
| D-07 | Duplicate rule in the database | `appointment` carries `doctor_id` and `appt_date` (denormalised from the slot) so "one active booking per patient, doctor and day" is a partial unique index, as the database design asks. | A partial unique index cannot reach through a join. |
| D-08 | Waiting list | `join_waiting_list` requires `confirmed: true` (the tool table omits it, but every write needs consent and US-05 says "when I agree"). Joining is refused with `SLOTS_AVAILABLE` if a free slot exists on the requested dates. A freed slot is offered to the **earliest matching** waiting patient and **held** for them for 2 hours (never later than 15 minutes before the slot); held slots are invisible and unbookable for everyone else. Lapsed offers return the entry to the list and pass the slot on. Booking that doctor in any other way fulfils the entry and releases its hold. Statuses: `active`, `offered`, `fulfilled`, `cancelled`. | FR-14/TC-07: "offered the slot first" needs a hold, otherwise anyone could take it. |
| D-09 | Extra columns | `slot.held_for_patient_id/held_until`; `queue_entry.patient_id/scheduled_at/requeued_at`; `queue_session.status/doctor_status/delay_minutes/busy_until/closed_at`; `app_user.username/display_name`; `audit_log.role` (docs §11 says role is recorded); `appointment.doctor_id/appt_date/updated_at`; `waiting_list.offered_slot_id/offer_expires_at/created_by/created_at`; `handoff_ticket.user_id`. Still exactly 17 tables. | Needed by the rules above; no new tables. |
| D-10 | Queue event types | Besides the five listed (break, delay, emergency, missed_turn, unavailable), `queue_event` also logs check_in, walk_in, call, consult_start, consult_end, return, priority, resume and session_closed. | The append-only log then fully describes a day, which the wait-time model (Phase 3) trains on. |
| D-11 | Appointment source | `source` allows `agent`, `staff` and **`simulator`**. | Synthetic history must be distinguishable from real demo actions. |
| D-12 | Embeddings | `kb_chunk.embedding` is `vector(384)` (multilingual MiniLM/e5-small class models); full-text search uses the `simple` configuration. The model itself is chosen in Phase 2. | Neon's 0.5 GB limit (docs §6); no stemmer exists for Hindi/Marathi in Postgres. |
| D-13 | Write tools are atomic and always audited | Every write runs in a savepoint. On success the audit row stores the result; on a rule failure the savepoint is rolled back (nothing partially executes) and an audit row with `{"ok": false, "error": CODE}` is still written. Callers commit after both. | FR-33 "all write actions"; failed permission attempts are security-relevant. |
| D-14 | Error codes | Added `VALIDATION_ERROR` (400), `FORBIDDEN` (403), `NOT_FOUND` (404), `INVALID_STATE`, `ALREADY_CHECKED_IN`, `ALREADY_ON_LIST`, `SLOTS_AVAILABLE` (409); `CONFIRMATION_REQUIRED` and `POLICY_WINDOW` are 422. | The spec names only a few codes. |
| D-15 | Injected clock | Every service function takes an optional `now`. | The simulator replays any day and tests are deterministic. |
| D-16 | Check-in | Possible only on the appointment day, by staff or by the patient / linked caregiver (API spec: "Staff, owner"). A patient can be in a doctor's queue only once. | |
| D-17 | Walk-ins | Staff only. A new walk-in patient needs name, birth year and a 10-digit mobile number, which is stored masked. | Docs §11 permission table; minimum data. |
| D-18 | Doctor events | `break`, `delay` and `emergency` take minutes and make the doctor busy until then; the doctor becomes available again automatically when that time passes (or by an explicit `resume`). An emergency interruption shows as `delayed`. | Doctor statuses in the WebSocket spec are available, on_break, delayed, unavailable. |
| D-19 | Privacy | Phone numbers are stored only in the masked form `+91 98XXXXXX10`, enforced by a CHECK constraint. Masking runs on audit arguments/results, queue event payloads, notifications and on every log record (installed as a log-record factory so handlers added later, e.g. by Alembic or Uvicorn, are covered). | NFR-08, TC-18. |
| D-20 | Fictional hospital | "Indravani General Hospital", 8 departments, 18 doctors, 400 synthetic patients; demo accounts `asha` (patient), `rajan` (verified caregiver of Vinayak Deshmukh), `sunil` (unverified link, must be refused), `priya` (staff), `mehta` (admin). | Personas from the PRD. |
| D-21 | Simulator assumptions | Occupancy 50–85 %, no-show 10 %, late arrival 8 %, walk-in load 10–35 % of capacity, start delay ~exp(6 min) plus 10 % big delays, 40 % chance of a break, 12 % emergency interruption, 1.5 % doctor unavailable, 4 % missed turn (85 % return), consultation length log-normal around the doctor's slot length × a per-session speed factor. Parameters are in `simulator/day.py` (`SimParams`). | Noise on purpose (risk R09); documented so results are interpreted correctly. |
| D-22 | Python version | Target Python 3.11 (Docker image and CI). `numpy` is pinned to 2.4.x because 2.5 requires Python 3.12. | Spec: Python 3.11+. |
| D-23 | API in Phase 1 | Only `GET /api/v1/health` exists. The other endpoints come with the agent in Phase 2 and call the same service functions. | Phase plan: chat API is Phase 2. |

## Phase 2 — Agent + RAG

| ID | Topic | Decision | Why |
| --- | --- | --- | --- |
| D-24 | Conversation state | Added an 18th table, `conversation` (history, summary, pending confirmation card, counters). | Chat state, the 5-minute confirmation cards and the per-session message cap must survive across requests and processes. |
| D-25 | Knowledge base | 357 Markdown documents (119 topics × English, Hindi, Marathi) in six collections: policies, insurance, departments, doctors, test_preparation, facilities. They are generated by `simulator/kb/` from structured content; translations share a `doc_key`. Policy numbers come from `app/tools/policy.py` and department/doctor facts from `simulator/hospital.py`, and a test fails if the committed files drift from the builder. Insurers, TPAs, companies and the Sahayata scheme are fictional; no medicine names appear anywhere. | "300+ docs", FR-17/FR-20, and documents that cannot contradict the code. |
| D-26 | Retrieval pipeline | Dense (pgvector cosine) and BM25, each top 20 → reciprocal rank fusion (k = 60) → top 12 → re-ranker → one result per translated section, swapped to the user's language → relevance threshold → top 4. BM25 runs in Python with a tokenizer that splits on whitespace and punctuation (Python's `\w` breaks Devanagari words), strips the nukta and maps Devanagari digits. The `tsv` column from the database design is kept for experiments. | Hybrid search with re-ranking (docs §5) that works for all three languages. |
| D-27 | Retrieval models | Defaults: `sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2` embeddings (384-d, Apache-2.0) and the `BAAI/bge-reranker-v2-m3-int8` cross-encoder (multilingual, Apache-2.0), both via fastembed/ONNX and baked into the Docker image. `*_BACKEND=auto` falls back to a deterministic local embedder (character n-gram TF-IDF + SVD) and a lexical re-ranker when the models cannot be loaded. Every vector records its embedder; queries compare only vectors from the same embedder (BM25 still answers otherwise), and `ingest --if-needed` re-embeds when the embedder changes. **In the development sandbox Hugging Face is blocked, so all retrieval results so far come from the fallback models; the neural path is covered only by adapter tests.** The cross-encoder's relevance threshold (0.15) is uncalibrated until the Phase 4 RAG evaluation. | Free tiers (docs §12) and honest reporting. |
| D-28 | Confirmation in code | The LLM can only *propose* a write. The agent runs the real tool in a savepoint that is rolled back (a preview with the exact checks), and turns the result into a confirmation card that expires after 5 minutes. The change is executed by the chat layer only after an explicit yes to that card: the Confirm button (sends `confirm_action_id`) or a short affirmative in English, Hindi or Marathi. Any other message drops the card. `confirmed` is not in any tool schema the LLM sees, and an extra `confirmed` argument is ignored. Confirmation questions and results are fixed, localised templates. | Rule 1: "confirmation before writes" lives in code, not in the prompt. |
| D-29 | Emergency check | Patterns in English, Hindi, Marathi and romanised Hindi/Marathi, plus a character n-gram logistic-regression classifier (flags at p ≥ 0.85) trained on its own examples. A match is ignored when it is negated ("no chest pain"), about the past ("heart attack last year") or exertion-only breathlessness. An emergency gets fixed guidance (112 / 108, the emergency department), no LLM call, and any pending card is dropped. The model can also call `emergency_redirect`, which blocks writes for the rest of the turn. The Phase 4 safety set will be written separately from the training examples. | FR-02/FR-03; recall first, but routine cardiology bookings must still work. |
| D-30 | Handoff | A ticket is created (no card) when the user asks for a person (detected in code, three languages), when the model calls `handoff_to_human`, or after three failed turns in a row (step limit, three invalid tool calls, or an empty reply). | FR-06. |
| D-31 | Citations and "don't know" | Citations come from the `[n]` markers in the reply; if knowledge was used and no marker survived, the top source is attached (FR-18). If every knowledge search found nothing and no other tool ran, the reply is replaced by a fixed "couldn't find this, shall I connect you to a person?" (FR-19), whatever the model wrote. | Grounding enforced in code. |
| D-32 | Medical-advice guard | Any LLM reply naming a medicine or a dose ("500 mg", "twice a day", "दिन में दो बार") is replaced by a fixed refusal pointing to a doctor. | FR-04. |
| D-33 | LLM interface | One OpenAI-compatible client serves Groq, Gemini (its OpenAI endpoint) and Ollama; models are configured as `provider:model`. On a 429 the provider is retried once after min(Retry-After, 4 s); other errors fall straight through to the next provider; if all fail, `/chat` returns 503 `LLM_UNAVAILABLE`. Temperature 0, at most 512 output tokens. | NFR-11, NFR-16, docs §12. |
| D-34 | Token budget | Tokens are estimated as Latin characters ÷ 4 + other characters ÷ 2. Each step sends the system prompt, only the role's tools (schemas simplified to ~890 tokens), the last 2 turns in full, 4 earlier turns as text, and a deterministic one-line-per-turn summary of anything older. Oversized tool results in the current turn are shortened. Retrieved chunks are capped at 700 characters × top 4. | `PROMPT_TOKEN_BUDGET` = 3,000 (docs §12). |
| D-35 | Language | Detected from script and frequent function words (Devanagari: Hindi vs Marathi; romanised Hindi/Marathi too); a bare "yes"/"no" keeps the conversation's language. | FR-01. |
| D-36 | Auth and quotas | Demo bearer tokens are HMAC-signed (12 h) and carry user, role and a session id; the role must match the user's record. `/chat` allows 20 messages per token session (429 with Retry-After until the session ends) and 60 per IP per hour (in memory; the demo runs one process). Chat is for patients and caregivers only. | docs §7, NFR-09. |
| D-37 | Tracing | Every turn writes a JSON-lines trace (`TRACE_DIR`, one file per day, phone numbers masked) with each LLM call (provider, model, latency, tokens, list-price cost estimate) and each tool call; the last 200 stay in memory for the Phase 5 dashboard. Langfuse is not connected (not reachable from the development sandbox). | NFR-14; the spec allows "a simple JSON trace log". |
| D-38 | Errors | Added `UNAUTHORIZED` (401), `RATE_LIMITED` (429), `LLM_UNAVAILABLE` (503) and `INTERNAL_ERROR` (500, no details leaked); request validation errors are 400 `VALIDATION_ERROR`. `/health` returns 200 "degraded" when the database is fine but no LLM key is configured. | docs §7 error format. |
| D-39 | Queue tools | `get_queue_status` and `predict_wait_time` are added with the queue engine's live features in Phase 3. | Roadmap: "queue tools for the agent" is Phase 3. |

## Phase 3 — Queue + ML

| ID | Topic | Decision | Why |
| --- | --- | --- | --- |
| D-40 | Breaks never reorder the queue | The merge rule projects the doctor's day from `max(now, OPD start)`; breaks, delays and emergencies are left out of that projection, and are instead added to every wait estimate. Before this, a break could make booked patients "due" and push walk-ins back. | TC-10 requires positions to stay unchanged after a break; nobody should lose their place because the doctor stepped out. |
| D-41 | Prediction target | wait = *known unavailability* (break / delay / emergency remaining, or time until OPD opens) + *residual*. The model learns only the residual, the time from the doctor being free until the consultation starts. TC-10 is read as: positions unchanged, the unavailability part shifts by exactly the break length, and each estimate rises by at most that much (less for booked patients whose slot is after the break, who would have waited for their slot anyway — measured: 12.6–20.0 min for a 20-minute break). | A break moves estimates through a known, exact term instead of hoping the model learns it. |
| D-42 | Features without leakage | `state_at(records, t)` rebuilds the queue at time t from stored entries, events and bookings, using only timestamps up to t. Training (one row per queue event × waiting patient over replayed days) and live prediction call the same function. Features: position, people ahead, kind, priority, minutes waited, slot offset, booked/walk-ins ahead, booked patients not yet arrived, queue length, slot length, the doctor's historical average (from the training days only), today's running consultation mean and count, time in the room, time since OPD opened, hour, weekday, merge rule. | One code path removes train/serve skew. |
| D-43 | Model and range | LightGBM: L1 (median) for the estimate, 10th and 90th percentile models for the range, then conformal adjustment on the validation days to aim for ~80% coverage (target 75–85%). Early stopping on validation. Artifacts (three text boosters + `meta.json`) are committed in `app/ml/artifacts/`; without them the app uses "people ahead × doctor's average" with a ±40% range. | docs §14.3; a range is more honest than one number. |
| D-44 | Training data | `python -m simulator history --days 90` into a separate training database (`careflow_train`); calendar split: days 1–60 train, 61–75 validate, 76–90 test (Sundays have no OPD). History replays skip live predictions (they would add hundreds of thousands of rows); a single `replay-day` keeps them. The deployed database never needs the history. | docs §14.3; Neon's 0.5 GB limit. |
| D-45 | Baselines | "position × 10 minutes" and "position × the doctor's historical average", where position is the 1-based place among waiting patients — the literal definitions in docs §14.3. | Gate: the model must beat both on MAE. |
| D-46 | Live predictions | After every queue event (engine), a `wait_prediction` row is appended for every waiting patient (TC-11). Between events the latest estimate is aged by the minutes that have passed. Estimates are shown rounded to 5 minutes: "about 35 min (25–50)". When at most 3 people are ahead, one mocked "your turn is near" message is sent per patient and session. | FR-24, FR-25, docs §8. |
| D-47 | Live push | `/ws/queue/{session_id}?token=…` sends `queue.updated` (tokens, positions, statuses — never names), `prediction.updated` and `doctor.status` after every change made through the API; an in-process broadcaster hands messages from the request threads to the socket's event loop. Staff and admins may follow any session, patients and caregivers only a session their patient is queued in. `GET /queue/entries/{id}/status` is the polling fallback. | FR-26, NFR-02. |
| D-48 | Queue endpoints | Besides the documented ones: `GET /queue/sessions`, `GET /queue/sessions/{id}`, `GET /queue/mine`, `POST /queue/sessions/{id}/call-next`, `POST /queue/entries/{id}/start|end|missed|return`, `POST /queue/sessions/{id}/close`. For `POST /queue/entries/{id}/check-in` the id is the **appointment** id, because the queue entry is created by the check-in. | The front desk (S6/S7) needs these actions. |
| D-49 | Agent queue tools and FR-27 in chat | `get_queue_status` (today's entries for the user's patients) and `predict_wait_time`. Patients whose appointment was cancelled because the doctor is unavailable get a note in the agent's context so it offers a new slot (rescheduling is free and allowed now). | US-08, US-12. |
| D-50 | Gemini fallback model and 503 retry | `LLM_FALLBACK` default changed from `gemini:gemini-2.0-flash` to `gemini:gemini-3.5-flash`. Tested on 19 Oct 2026 through the OpenAI-compatible endpoint with the 12 patient tools: `gemini-2.0-flash`, `gemini-2.5-flash` and `gemini-2.5-flash-lite` return 404 ("no longer available to new users"); `gemini-flash-latest` calls tools correctly but took 8–12 s; `gemini-3.5-flash` made the correct `search_doctors` call in 1.3–1.8 s. A 503 ("model is experiencing high demand"), seen often on the free tier, is now retried once after a short wait, like a 429, before falling back; other 5xx errors fall back straight away. | The documented model no longer exists; NFR-01 needs a median reply under 4 s. |
| D-51 | Gemini thought signatures and retriever warm-up | Gemini 3 models return a `thought_signature` with each function call and reject the next request of the same turn (HTTP 400) unless it is sent back. Tool calls now keep the provider's `extra_content` and send it back to Gemini; calls Gemini did not make (the chat layer's confirmed write, or a step served by another provider) get Google's documented placeholder signature, and the field is removed for Groq and Ollama. The API also loads the retrieval models in a background thread at start-up (`WARM_UP_RETRIEVER`), so the first question does not wait for them. | Found in a real end-to-end chat: every multi-step turn on Gemini failed, and the first question waited 90 s while unreachable models were retried. |

## Phase 4 — Evaluation

| ID | Topic | Decision | Why |
| --- | --- | --- | --- |
| D-52 | LLM models (revisits D-00 "Groq primary") | Groq retired `llama-3.3-70b-versatile` (404 on 20 Oct 2026). Defaults are now `groq:openai/gpt-oss-120b` (primary; correct tool calls in 0.6–0.9 s) and `gemini:gemini-3.5-flash-lite` (fallback). A 429 that names a *daily* quota is not retried (it cannot succeed today); the next provider answers at once. Provider errors are logged with the provider's error code only, never its message, which can echo the conversation. | The documented models no longer exist; free daily quotas are the binding limit. |
| D-53 | Emergency gate, second version | Patterns are grouped by what is happening (heart, breathing, not responding, stroke, bleeding, seizures, self-harm, poisoning, allergy, injuries, pregnancy, children) and checked per clause: a clause about the past ("as a toddler", "in 2023") does not count unless it also says "now"; questions about the emergency department or ambulance number are information requests; the bare word "emergency" no longer flags. Generic words ("poison", "accident", "fits") flag only if the classifier gives at least 0.2. The classifier was retrained on 600 extra examples written by a separate author who did not see any evaluation set (`app/safety/emergency_training.jsonl`), with character and word n-grams; thresholds come from 5-fold CV on the training data (`python -m app.safety.emergency_tune`). It runs only on messages of 4+ words: short replies like "नहीं" had scored 0.97. Method: version 1 was measured once on held-out set 1 (29/40, 9/40 false alarms), then held-out set 2 — written by another author who saw neither the detector nor the other sets — was used for the final measurement. | The first evaluation run caught only 19/40 emergencies in code (the LLM caught most of the rest) and raised 9/20 false alarms. Recall must not depend on the LLM (non-negotiable rule 3). |
| D-54 | Retrieval threshold and grounding rule | The lexical re-ranker's relevance threshold is 0.275, chosen by 5-fold cross-validation on the RAG set (accuracy over answerable + unanswerable questions); 0.55 had left a third of answerable questions without a source ("What are the OPD timings?" failed live). Because weak sources now reach the model, the code adds a grounding rule: a reply after a knowledge search that cites none of the retrieved sources (and used no other tool) is replaced by "I couldn't find that in the hospital's documents" with a handoff offer. The cross-encoder's threshold (0.15) could not be re-tuned here because the model cannot be downloaded in this environment. | FR-18/FR-19 as a rule in code rather than a prompt instruction. |
| D-55 | Analytics backend now, UI in Phase 5 | Built now because the unsafe-analytics safety set needs it: `reporting.*` views without patient names or phone numbers (migration 0003), a NOLOGIN `careflow_analytics` role with SELECT on those views only, a SQL validator (sqlglot: exactly one SELECT; no INTO, locks, recursive CTEs, generate_series or functions outside an allow-list; only the reporting views), execution in a READ ONLY transaction with a 3 s statement timeout and a row limit, and a refusal in code of requests to change data before any LLM call. `POST /api/v1/admin/analytics` (admin only). | FR-30, FR-31, TC-14, TC-15; docs §11 "SELECT-only grants on reporting views". |
| D-56 | Evaluation harness | `python -m eval.*` uses a separate database (`careflow_eval`) seeded once for Monday 19 Oct 2026 (seed 42); every conversation runs in one transaction that is rolled back, with the clock fixed at 08:00. The evaluated LLM is one model with no fallback, so each result belongs to the model it names; per-minute limits are waited out, a daily limit stops the run, and responses are cached on disk so an interrupted run resumes without spending quota. Datasets were written separately from the code under test: RAG questions and safety cases by authors who were told not to copy the detector's patterns, and the held-out emergency sets by authors who could not see the code at all. | Rule 7: every number comes from a run that can be repeated. |
| D-57 | Running the evaluation on free tiers | The user chose free tiers only. `python -m eval.nightly` works through the remaining evaluation in priority order — agent run 1, RAG answers, agent runs 2–5, baseline run 1, baseline runs 2–5, then the safety sets — skipping any step whose model has used its daily quota; a scheduled check-in ran it every 6 hours (stopped on 20 Oct 2026 at the user's request; what was not run is listed in the README). Runs cut short by a quota are discarded, never counted. Every run starts with the id sequences reset, so ids (and therefore prompts) repeat exactly and an interrupted or repeated run is answered from the response cache. Turn latency is measured as local work plus each LLM call's original API time, so rate-limit waits and cached replays do not distort it. | Free quotas allow about 25–30 agent conversations a day; the full plan (600 agent runs, 600 baseline runs, 150 graded answers) takes weeks, and every number must say how many runs it is based on. |
| D-58 | What "baseline version" means | §14 defines it as basic dense RAG, a single-prompt agent and position × 10 minutes. Here: the same LLM, prompt and tools with every code-level safeguard switched off (`eval/baseline.py`): writes execute when the LLM calls the tool (no confirmation card), no emergency check before the LLM, no medicine filter, no grounding rule, no injection filter, and dense-only retrieval with no threshold. It is applied by patching inside the evaluation only. For retrieval the baseline is fixed-size chunks with dense search; for the wait time it is position × 10 minutes. | Shows what the rules enforced in code are worth, with everything else held equal. |

## Phase 5 — Ship

| ID | Topic | Decision | Why |
| --- | --- | --- | --- |
| D-59 | UI stack and serving | Vite + React with hand-written CSS (no component library). FastAPI serves the built app (`ui/dist`) on the same origin and port as the API, with index.html for client-side routes, so one container serves everything. Fonts (Noto Sans and Noto Sans Devanagari) are bundled, so pages make no third-party requests. Interface text lives in `ui/src/i18n.js` in English, Hindi and Marathi; a unit test fails if any string or placeholder is missing in a language. | Hugging Face Spaces exposes one port; Devanagari must render without network fonts. |
| D-60 | Endpoints the screens needed | `GET /staff/today` (doctors on duty with their bookings and check-in state — sessions only exist after the first check-in), `POST /staff/doctors/{id}/session` (so a break or unavailability can be recorded before anyone arrives), `GET /admin/dashboard` (FR-29, FR-32: the evaluation numbers are read from the result files shipped in the image, never computed in the page; latency and cost come from this server's recent traces), `POST /admin/reset` (FR-34, admin only, demo mode only, with a 15 s lock timeout). | S6–S8 and TC-17. |
| D-61 | Card expiry on the client | The chat reply also carries `expires_in_seconds`; the page counts down from when the reply arrived. | A phone whose clock is off by minutes would otherwise show live cards as expired, or expired ones as live. The server still decides. |
| D-62 | Long-running demo | Slots for the next 21 days are topped up at every start (`simulator seed --if-empty`) and every 6 hours by the API (only missing slots are added). | Found while preparing the deployment: after 21 days a deployed demo would have had nothing left to book. |
| D-63 | Browser tests and the demo video | `tests/e2e/server.py` runs the production app with its own database, a clock that starts on Monday 19 Oct 08:00 IST, and a rule-based stand-in for the LLM, so the 15 Playwright tests are repeatable without API keys (flows on all nine screens, TC-17, TC-20 under 2 s, axe-core WCAG A/AA with no serious or critical violations, 360 px with large text and 44 px tap targets). The demo video is recorded by `tests/e2e/record_demo.py` with the real LLM. | Real-model behaviour is measured by the evaluation suite; the browser tests check the screens and the rules. |
