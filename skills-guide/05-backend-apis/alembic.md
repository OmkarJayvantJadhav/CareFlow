# Alembic

## 30-second answer
Alembic is the database **migration** tool for SQLAlchemy: each schema change is a versioned Python script with `upgrade()` and `downgrade()` functions, chained by revision ids, so every environment (laptop, CI, production) can be brought to the same schema with **`alembic upgrade head`**. CareFlow has **12 migrations** (`0001_initial_schema` … `0012_messaging`). The Docker entrypoint runs `alembic upgrade head` on every start, the test suite migrates a fresh database once per run, and migration `0003` creates **reporting views and a SELECT-only database role** used by the analytics agent.

---

## Basics you must know

### Why migrations?
Code and schema must change together. Hand-written `CREATE TABLE` scripts drift; `Base.metadata.create_all()` can't alter existing tables or keep history. Migrations are version control for the schema.

### Files
```
alembic.ini              # config (script location, logging)
alembic/env.py           # how to connect; target_metadata for autogenerate
alembic/script.py.mako   # template for new migrations
alembic/versions/*.py    # the migrations
```

### A migration
```python
revision = "0003"
down_revision = "0002"

def upgrade() -> None:
    op.create_table("department", sa.Column("id", sa.Integer, primary_key=True), ...)
    op.add_column("patient", sa.Column("email_enc", sa.Text(), nullable=True))
    op.create_index("ix_x", "table", ["col"])
    op.execute("CREATE EXTENSION IF NOT EXISTS vector")

def downgrade() -> None:
    op.drop_column("patient", "email_enc")
```

### Commands
| Command | Does |
|---|---|
| `alembic revision -m "msg"` | New empty migration |
| `alembic revision --autogenerate -m "msg"` | Compare models with the DB and draft a migration (always review it) |
| `alembic upgrade head` | Apply all pending migrations |
| `alembic downgrade -1` | Undo the last one |
| `alembic current` / `history` | Show state |
| `alembic upgrade head --sql` | Offline mode: print SQL instead of running it |

The DB stores the current revision in the `alembic_version` table.

### Good practices
- Review autogenerated migrations (renames look like drop + add!).
- Data migrations: backfill in steps (add nullable column → fill → set NOT NULL).
- Never edit a migration that has run in production; add a new one.
- Keep migrations runnable on an empty database (CI does this).

## How I used it in CareFlow

### The 12 migrations (`alembic/versions/`)
| # | Purpose |
|---|---|
| 0001 | Initial schema — and `CREATE EXTENSION IF NOT EXISTS vector` for pgvector |
| 0002 | Conversation and knowledge-base metadata |
| 0003 | **Reporting views + SELECT-only analytics role** |
| 0004 | User accounts |
| 0005 | Calendar and reminders |
| 0006 | Registration and check-in |
| 0007 | Queue management |
| 0008 | Account management |
| 0009 | Hospital setup |
| 0010 | Real patient data (encrypted contact details) |
| 0011 | Editable documents and policy |
| 0012 | Messaging (SMS / e-mail) |

### `env.py` (`alembic/env.py`)
- `target_metadata = Base.metadata` (from `app/db/models.py`) for autogenerate.
- URL from the app's settings via `normalize_url()` (accepts Neon's `postgres://` URLs), unless a test sets `sqlalchemy.url` explicitly.
- Uses `NullPool` and the same `connect_args` (`prepare_threshold: None`) as the app, for Neon's pooler.

### Migration 0003 — security in the schema
```python
op.execute("CREATE SCHEMA IF NOT EXISTS reporting")
for name, body in VIEWS.items():
    op.execute(f"CREATE OR REPLACE VIEW reporting.{name} AS {body}")
```
- Views over appointments, slots, queues, waiting list and predictions **without patient names or phone numbers** (patients appear only as `patient_ref`, birth year and language).
- A `DO $$ … $$` block creates role `careflow_analytics` (NOLOGIN), grants `USAGE` on the schema and `SELECT` on the views, and grants the role to the app user — wrapped in `EXCEPTION WHEN insufficient_privilege` so hosts that forbid `CREATE ROLE` (some managed Postgres plans) still get the views.
- `downgrade()` drops the schema with `CASCADE`.

### Where migrations run
- **Docker entrypoint** (`docker/entrypoint.sh`):
  ```sh
  alembic upgrade head
  python -m app.manage prepare          # demo seed / first admin
  timeout 600 python -m app.rag.ingest --if-needed || echo "...starting anyway"
  exec uvicorn app.api.main:app ...
  ```
- **Tests** (`tests/conftest.py`): drop and recreate the `public` schema, then `command.upgrade(cfg, "head")` once per test session — so every CI run proves the migrations work from scratch.
- **Local dev:** `alembic upgrade head` after `docker compose up -d db`.

## Interview questions

**Q: Why not `create_all()`?**
It only creates missing tables; it can't alter columns, add indexes to existing tables, migrate data or record history. Migrations are repeatable and reversible.

**Q: What does autogenerate miss?**
Renames (seen as drop + add), some constraint/type changes, views, extensions, roles, data migrations — they must be written by hand (like 0003's views and role).

**Q: How do migrations run in production?**
At container start before the server: `alembic upgrade head` then Uvicorn. With several replicas you'd run it once as a release step instead.

**Q: How do you add a NOT NULL column to a big table?**
Add it nullable, backfill in batches, then set NOT NULL (and a default) in a later migration.

**Q: What's `down_revision`?**
The parent revision; it forms the linked list Alembic walks to upgrade or downgrade.
